# Auspex V2 — working plan

**Status:** collaborative design, not an implementation mandate. See [STATUS.md](STATUS.md) for the current implementation snapshot. This document records decisions, assumptions, open questions, and the next small steps so we can resume the discussion without rediscovering them. **Do not implement the whole plan autonomously:** discuss interfaces and review each vertical slice together before proceeding.

## Goal

Evolve Auspex into a Python 3.13 general-purpose experimental-control system while retaining the V1 mental model: define an experiment as a Python class with parameters, instruments, outputs, a single-measurement kernel, sweeps, and a filter graph. Add a compilation boundary so a saved plan executes independently of changes to a Jupyter notebook. Preserve convenient direct Python access to instrument drivers. Support adaptive measurements and real CPU parallelism in the processing pipeline.

We are **not** building LabRAD, a distributed instrument service, a hermetic application packager, or arbitrary interrupted-run resumption. The initial deployment is local to one acquisition host. Qubit experiments remain a future compatibility target, not the first implementation target.

## Agreed design

### Experiment authoring and plans

**Reviewed compiler slice:** use the name **ExperimentServer** going forward. The initial offline implementation is documented in [experiment guide](../src/auspex_v2/experiment/experiment.md). `sequence(self, seq)` records typed expression/instruction trees; no saved Python source execution. `setup`, per-axis `sweep_begin`/`sweep_end`, and `teardown` use the same builder. Setup precedes unswept bindings; swept bindings apply outer-to-inner on every axis advance without deduplication. Fixed and joint sweeps retain V1 first-added-fastest ordering. Each explicit publication owns one complete window; the default scan encloses a full traversal. Instrument roles use a fixed `InstrumentKind` taxonomy. Abstract roles declare KIND; `driver=` or class-body `.bind(Driver)` infers it. Calls/bindings accept settling delays lowered to explicit WAIT instructions. Optional `InstrumentRef(kind=..., driver=...)` supplies an offline explicit API description for driver-shaped assignment, property reads, getters/setters, and operations via the shared live proxy with a recording-session backend. No driver instance is constructed; saved plans contain only plain descriptions/instructions. Proxy keyword arguments belong to the driver; runner waits use `seq.wait` or explicit `seq.*` syntax. IF/ELSE, REPEAT, bounded WHILE and TERMINATE form structured control flow. Submitted runs will be immutable, one active run with no queue. Completed scans survive cancellation, partial publication is deferred; successful runs normally retain connections. Every run will have a folder and human-readable execution.log with dispatch/outcome/control-flow annotations, not returned data. Users are trusted: basic correctness checks, not sandboxing or defense-in-depth security. The compiler and offline harness integrate explicit publication with real filter workers using injected fake instrument results; the separate first ExperimentServer now provides real waits and commands through the explicit driver registry, durable status and best-effort logs (see experiment/server.md). The compiler review separates plain-plan normalization, read-only validation, and stable ID assignment; checks parameter availability at phase/sweep boundaries, detaches parameter metadata, normalizes NumPy settings, validates known comparison types, and copies fake command arguments/readbacks. The current plan format is version 5, with explicit sequence point boundaries; versions 1–4 now fail with recompile guidance (WIP plans have no backward-compatibility guarantee). The follow-up minimize-surprise patch rejects declaration shadowing and recording-time configuration edits; explicit `seq.set_parameter()` updates unswept runtime parameters and applies their bindings/waits, with runtime type/bounds checks. Swept runtime updates remain rejected pending adaptive sweep/coordinate design. Runtime-updated parameters are not frozen repeat counts; loop bounds stay fixed, while WAIT can read an initialized unswept parameter's current value. Proxy routing and driver kwargs now use separate namespaces. Reflected arithmetic/unary negation and configuration summaries in `explain()` are implemented. Buffer producer/nonblocking queue methods are private; receive/drain/view/clear remain the public data interface.

- Continue to use Python experiment classes and familiar concepts such as class-level parameters, output connectors, `add_sweep(...)`, and explicit pipeline connections (V1's `set_graph(...)` is not a V2 API). V1 references: `src/auspex/experiment.py`, `src/auspex/parameter.py`, `src/auspex/stream.py`, `doc/experiments.rst`.
- `exp.compile()` freezes and validates the configured experiment into a saved, inspectable plan; `auspex.run(plan)` executes it. Editing notebook variables or the original experiment after compilation must not alter that plan. A freshly started controller must be able to **start** a supported saved plan without re-running the notebook. No requirement to resume a failed or interrupted run.
- Arbitrary imperative V1 `run()` code cannot be converted reliably into a portable command program. The reviewed `sequence(self, seq)` method constructs typed instructions for one measurement, while sweeps repeat it; the offline compiler implements this builder API. The plan can encode allowed control flow and adaptive decision points, without knowing in advance which path observations will select.
- Compilation should validate command parameters, instrument capabilities, sweep/axis and filter schemas, permitted transitions, and bounds. It need not inspect arbitrary filter code or package an entire Python environment. Hardware connections occur at run time, not while declaring classes or compiling.
- A supervised experiment runner interprets the saved plan; it does not execute recorded experiment source. Plan format needs a small explicit version number and a readable `explain()` representation. Keep code/plugin compatibility checks pragmatic rather than promising perpetual portability. The notebook/CLI/GUI is only a client: disconnecting it must not stop an active run.

### Adaptivity

- A measurement and its completed processing result enter a decision point. A **pure decision function** receives the result, explicit previous policy state, and frozen configuration, and returns proposed next settings and/or sweep points, updated policy state, or stop/failure. The experiment runner validates bounds and iteration limits, records the decision and its inputs, then requests commands through its exclusive instrument-server session. No instrument handles or side effects inside decision functions; randomness, if needed, is represented by explicit state/seed.
- Built-in, versioned policies support saved-plan execution immediately. Custom policies can be referenced by module/function with a code/version check. Truly reusable experiment definitions and decision functions should be committed to the Auspex repository as a **human/lab practice**, not a source-control rule enforced by `compile()`.
- Notebook-only decision functions are useful for exploration. Their source may be saved for human inspection, but a saved plan **must fail preflight** if its executable decision function is unavailable to a freshly started controller. Never execute logged source as an implicit fallback or silently substitute a changed policy.
- Do not claim that identical plans produce identical physical measurements or adaptive paths: record actual commands, observations, decisions, and sweep coordinates. Distinguish replaying recorded decisions from recomputing them if replay is added later.

### Local services, control, and instruments

- Run **two independent, persistent local programs** on the acquisition host, started explicitly rather than launched by a notebook. The **instrument server** owns registered-instrument inventory, exclusive run/live sessions, worker processes, failure/recovery state, and instrument events. The **Auspex experiment coordinator** accepts saved plans, supervises experiment-runner and filter processes, owns run status/results, and records experiment events. Notebook, CLI, and future GUI clients connect to these programs; they do not own the backing processes. A notebook can disconnect and reconnect while a run continues.
- Standardize Auspex V2 desktop GUIs on **pyqtgraph with PySide6/Qt Widgets**; Qt is an optional client-side dependency, never required by headless services or drivers. The [instrument server GUI prototype](../src/auspex_v2/instruments/server/instrument_server_gui.md) is an optional **inventory and connection-management client**: it can connect/disconnect, recover/quarantine, disconnect all, and clear inventory, and can discover/identify/register VISA candidates in a separate Add instruments window, but cannot open live sessions, change settings, read measurement data, or acquire. Per-device termination without a mandatory reason and a server-side `TERMINATE_ALL` operation are implemented for simulated workers. A software worker kill is not a physical emergency off.
- There is **one authoritative instrument server per acquisition host**, not a new instrument server for each experiment. Each experiment runner uses exactly one exclusive run session with it; this is the intended one-to-one *session* relationship, not process ownership. Instrument server registration/leases provide the host-wide authority that prevents independently submitted runs or live clients from claiming the same domain. Initially, allow only one active run per host. Define the lifecycle and protocol boundary before implementing experiment authoring.
- Use a small local-only IPC request/reply protocol and explicit connection/version handshake; unlike V1's plot server (`../utils/auspex-plot-server.py`), do not bind instrument control to all network interfaces by default. The instrument server now uses a permission-restricted Unix socket with versioned JSON control and bounded inline binary results for VNA-scale arrays; **high-rate digitizer data must not use that by-value path**. Experiment-coordinator IPC, cross-service discovery, and stronger operator authentication remain undecided.
- Instruments registered with the instrument server constitute an exclusive laboratory domain. At the start of an experiment, **lock out interactive Auspex access to all registered instruments**, not just the devices used by that experiment (analogous to remote mode). Lockout is not a command to reset or configure unused hardware. To use one independently during a run, de-register it *before* the run. Registration/de-registration and recovery are explicit, logged actions; de-registration must not bypass an active run or an unsafe/uncertain state. This protects cooperating Auspex clients, not someone connecting outside Auspex directly.
- A driver remains easy to use in a notebook or a quick Python loop while no experiment holds the domain. **Registered** instruments are accessed interactively through a client of the independent instrument server (prefer a synchronous proxy over a second unmanaged connection); the same lockout rules apply. **Unregistered** instruments can still be used directly as ordinary Python drivers. Experiment orchestration must not be required for simple lab scripting.
- Default proposal: one spawned **process-backed worker per active physical instrument connection**, rather than per channel, for independent termination and native-library isolation. Each worker constructs/connects its driver inside its process and serializes its commands. Benchmark startup and IPC; thread-backed workers could be an explicit exception, but Python threads cannot be forcibly terminated safely.
- Lightweight server-to-worker command language: **`GET`, `SET`, and `CALL`** with typed arguments/results, timeouts, and an allowlist/capability declaration. The current prototype has these operations and bounded results, plus a session-bound driver-shaped proxy discovered from declared capabilities and optional keyword arguments on GET/SET; typed argument schemas, correlation IDs, and richer capability discovery remain proposed. `GET`/`SET` address declared commands or managed properties; `CALL` addresses explicitly registered handwritten methods and may return data, trigger acquisition, or both. Do not infer wire operations from return type or method name; generated Python `get_`/`set_` helpers are not extra `CALL`s. Avoid exposing arbitrary raw SCPI or arbitrary method invocation to compiled plans. Batch commands when appropriate. VNA-scale arrays travel as bounded binary payloads after control response envelopes; eventual high-rate acquisition must use a separate buffer path.
- **Reviewed server lifecycle (trusted laboratory implementation):** inventory, connection health, and ownership are separate. `register()` records a physical identity as `DISCONNECTED` with no worker/I/O. Explicit `connect(name)` (or `run.connect(name)` under the run lease) constructs/connects a process worker; live access and commands require `CONNECTED`. Closing a live lease does not disconnect. Graceful `disconnect(name)`/`disconnect_all()` leaves registrations intact. Connect/disconnect failure latches `UNKNOWN`; worker death, command failure, or operator termination latches `TERMINATED`. Recovery is a manual acknowledgement that returns to `DISCONNECTED`, **not** a reconnect or physical safety check. `TERMINATED` devices, even those with no worker, can be quarantined; `TERMINATE_ALL` latches every registration without releasing ownership. Only fully disconnected, unowned inventory can be cleared and persisted empty. An orphaned run requires explicit reconciliation before these cleanup actions. On clean service exit workers disconnect but registrations remain; unexpected service loss makes previously connected devices uncertain. The explicit `-c` startup override forcibly discards even uncertain/orphaned state without hardware I/O; it is an operator reset, not physical recovery.
- A terminated or unexpectedly dead worker has an unknown command outcome; do not silently retry, release ownership, or infer physical safety. Durable operator identity, device-specific readback/recovery checks, safe shutdown and hardware interlocks remain future work. Killing a process does not switch off a source or stop a magnet.
- If the **experiment coordinator or runner** dies mid-run, the instrument server must not infer that the domain is free: retain the lockout and require explicit reconciliation of the orphaned/uncertain session. If the **instrument server** dies, the experiment fails and hardware state is treated as uncertain. Restarting either program does not automatically resume the run. Define recovery after normal shutdown, client disconnect, and process crash separately.
- Preserve V1's declarative driver authoring (SCPI commands, generated properties and `get_`/`set_` methods, value conversion and bounds) without copying its class-name-dependent metaclass or eager import of all drivers (`src/auspex/instruments/instrument.py`, `src/auspex/instruments/__init__.py`). Keep command definitions inspectable for server metadata. Explicitly implemented operations/properties must also be registerable: **SCPI descriptors are not mandatory for every instrument**. Custom acquisition drivers such as X6/Alazar currently couple reception to output connectors and will need streaming adapters; a command-only wrapper is not sufficient.
- Holzworth (`src/auspex/instruments/holzworth.py`) is the counterexample to a SCPI-only design: it has USB/DLL backends, handwritten properties, limits learned at connection, and multiple logical channels on one physical device. Resource ownership must use a physical-device identity (e.g. serial shared across channels), not assume a worker per channel. Importing a driver must not probe/reset hardware or load an unavailable backend; connect explicitly inside the worker and report failures rather than substituting a `MagicMock`. Test these constraints with a fake multichannel backend before porting Holzworth.

### Filter pipeline

**Reviewed manual-use slice implemented:** standalone `AuspexStore` writes are a first-class workflow; `ManualPipeline` wraps whole-window submission without instrument control, partial-window APIs, or filter-state inspection. Required `BufferSpec` endpoints retain bounded FIFO completed outputs (never previews), support consuming receive/drain and non-consuming view, return independent data, and survive successful graph closure. Full buffers warn once per full episode (subject to Python warning filters); backpressure/fail policy still applies, with no silent drops. See [manual guide](../src/auspex_v2/filters/manual.md) and `../examples/manual_data.py`.

- The **Filter Server** is the pipeline-supervising component of the eventual experiment coordinator, **not a third persistent host-wide daemon**. For each run it validates and instantiates a reconfigurable dataflow DAG, supervises filter workers, owns the bounded shared-memory allocations and their cleanup, and reports required results/failures to the experiment runner. Graph topology is fixed *during* a run but may differ between experiments. Filters can change validated parameters between completed windows using acknowledged configuration revisions; schema-changing updates are deferred.
- Keep V1-like output/input connectors and graph edges for authoring, but compile a dataflow DAG separate from the experiment control graph. A named, window-complete processing result bridges back to an adaptive decision; filters do not issue instrument commands.
- Prefer a **simple first implementation: one logical filter instance per spawned process**, with no automatic process-placement compiler or introspection of filter internals. Filter objects are constructed inside workers from importable definitions and plain validated configuration, not pickled from clients. The Filter Server allocates and owns a per-run memory budget; **slots belong to edges, not filters**. Each edge gets its own bounded shared-memory channel (a ring of reusable slots; separate regions per edge are sufficient initially, without a general-purpose contiguous arena). Producer writes a free slot; a small ready message carries slot ID, actual shape/length, schema and run/acquisition/window/sequence IDs; consumer releases the slot when done. Batch and window-end messages must retain per-edge order; configuration/control acknowledgements are separate. Small versioned, size-limited JSON messages are a starting point, not a commitment for high-rate notifications: benchmark before deciding on binary framing. Fan-out initially copies to each edge rather than introducing global reference counting. Benchmark before considering explicitly grouped filters or zero-copy fan-out.
- Define filters independently of process/queue inheritance: declared ports and schema transformation, `on_batch`, `on_window_end`, and lifecycle hooks. Retain axes, units, dtype, and unstructured/adaptive coordinates as explicit metadata. Completion of a window is an explicit ordered event, **not** a test for an empty queue. **The experiment runner owns acquisition windows** and emits `WindowEnd` after its last batch; the Filter Server confirms completion only after required results and persistence acknowledgements. **Groups belong to pipeline/filter configuration**, not to the experiment's acquisition protocol: the experiment may configure a group size or completion condition (e.g. five sweeps per average), but the relevant filter identifies its own group boundaries from completed windows and emits its group result. Different branches may use different grouping rules. A missing/incomplete group at run end is an error for a required result; the runner must not manufacture `GroupEnd` for every filter. Initial ports have stable dtype/rank/units and bounded size, but variable shapes and actual coordinates per window. Topology remains fixed during a run; external parameter changes are validated and acknowledged only between windows, while internal filter state may evolve within one. Initially defer multi-input joins and fail the required pipeline on worker/edge/result errors rather than silently propagate incomplete data.
- Support **multiple logical writer filters** in a run, each attached to its own graph output and configured with a dataset destination in the same `.auspex` folder (as in V1). Preserve one *physical* store/manifest owner per run: writer filters send bounded, required write requests to it; that owner serializes publication and acknowledges each completed dataset. This is sink multiplexing, not a general multi-input data-join filter. Validate destination collisions before execution and fail the run on write/acknowledgement errors; do not let concurrent writers race on the manifest.
- **Reviewed initial supervision contract:** a dedicated per-run Filter Server thread spawns and monitors workers. Start with one acquisition ingress and one input per filter, but support overlapping batches/windows immediately. Submission and completion waits are separate. Bound shared-memory edges, notification queues, outstanding windows, and retained terminal results; terminal consumers must drain required results concurrently when needed. Best-effort behavior is restricted to preview sinks, not arbitrary optional subgraphs.
- **Graph capacity policy:** `backpressure=True` (default) waits for capacity and propagates delays upstream without blocking supervision. `backpressure=False` fails on exhaustion of any required input, internal edge, notification, outstanding-window, or retained-result capacity. Neither mode drops required data or allocates an unbounded backlog. The supervisor latches the failure, stops admission, wakes callers, cleans up workers/memory, and exposes the failure to the future experiment coordinator, which must terminate experiment execution and report the error. For hardware that cannot pause, provision and benchmark adequate buffers/throughput; this is fail-on-overflow, not a throughput guarantee.
- Parameter updates pause admission and drain the admitted window prefix graph-wide, then validate/apply one filter-local revision. Draining windows need not finish an unrelated branch's group. The target filter rejects updates incompatible with its own active group. Adaptive acquisition waits for the named required result(s); ordinary predetermined acquisition can overlap processing. The VNA smoke test is not a digitizer throughput benchmark.
- **V1 filter migration audit:** preserve the behavior of one-input transforms (framing, integration, channelization, averaging, single-shot analysis), multi-output filters, and coordinate-aware adaptive results; do not port `Filter(Process)`, queue polling, mutable descriptor propagation, or eager imports. `ElementwiseFilter`/`Correlator` need an explicit multi-input join design and are *not* supported by the initial one-input runtime. Averager's partial outputs are distinct from required final results. Hardware stream selectors belong at acquisition/adapter boundaries; file writing and plotting are sinks with separate reliability policies. Kernel expressions, arbitrary callables and side-effecting calibration files need explicit reviewed replacements, not implicit source execution. Window-boundary handling must define partial-record carry, state reset/continuation, and schema-affecting parameter changes before those filters are migrated.

### Data, run log, and lab notebook

- Use V1's folder-based `.auspex` format (`src/auspex/data_format.py`) as a **conceptual**, not file-compatible, starting point. The V2 dataset store has a versioned manifest and separate completed numeric arrays with actual per-dataset coordinates and descriptors; it does not read V1 folders. Later add run-level metadata: frozen plan, decisions, status, and detailed run log. Do not assume fixed-size datasets suffice for adaptive/streamed acquisition.
- Include a human-readable **run report**, linked to machine-readable events and arrays. Best-effort source provenance: save a *non-standard experiment definition* and decision-function code used by that run when available. Source is for human reference only, not authoritative, guaranteed complete, or executable; do not dump full notebook history. Make capture failures visible. Consider secrets/file permissions when saving or sharing source.
- Maintain a **host-level lab notebook**: a sparse, readable timeline combining high-level events from the experiment coordinator (runs and user comments, with links to run folders) and instrument server (interactive connections, de-registration, worker failure, recovery). Define a single ordering/persistence mechanism for the combined timeline; neither program should invent the other's internal state. It is a backstop to human notes, **not a per-command trace**. Provide a separate current instrument view whose values are labeled last-commanded, last-observed, or unknown, rather than implying certainty about hardware state.
- On service restart, an interrupted run is incomplete/failed; instruments with uncertain physical state require reconciliation, not automatic resumption or automatic return to CONNECTED.

## First vertical slice: find a VNA resonance

Target existing `AgilentE8363C` (`src/auspex/instruments/agilent.py`), whose driver exposes `frequency_center`, `frequency_span`, `num_points`, and `get_trace()` returning frequencies and complex S-parameters. The simulated E8363C-like path remains automated coverage; the real E8363C/N5230A are now admitted for attended lab execution.

**Scenario:** acquire ~2000 points over ~1 GHz, find a candidate ~1 MHz-wide resonator, narrow the sweep, fit a Lorentzian, and finish with the fitted linewidth occupying roughly 50% of the final span (approximately 2 MHz for a 1 MHz linewidth). Specify whether the fit uses magnitude, power such as `|S21|²`, or a complex response, and whether it seeks a peak or dip. At 1 GHz / 1999 intervals the initial spacing is ~500 kHz: the first sweep has only ~2 samples across a 1 MHz feature. Use the coarse sweep for *candidate detection*, not a trustworthy linewidth fit; an intermediate sweep (e.g. ~20 MHz) may be required. Fit-quality checks, no-candidate behavior, edge-of-span behavior, frequency bounds, and a maximum number of refinements must be explicit.

**Pipeline/plotting acceptance extension:** repeat VNA sweeps on the same actual frequency grid and compute a bounded, pointwise **complex S21 average** across them. Each completed sweep is a window; an explicitly delimited averaging group may span multiple windows. Publish labeled partial-average snapshots (count and expected count, actual coordinates, group/window ID, configuration revision) for live plotting without skipping any required input; publish a distinct required final result only when the group completes. Require **exact equality of successive actual frequency-coordinate arrays** (same shape and values) before pointwise averaging; any mismatch is an error indicating a possible instrument problem, not something to tolerate or silently interpolate. If regridding is ever wanted, it must be a separate explicit, reviewed operation. Test previews while sweeps progress, plot disconnect/reconnect, group completion, and failure for incomplete or mismatched contributions. Parameter updates that invalidate the group must be rejected or begin a new explicitly recorded group; never silently mix configurations. Use a configurable number of sweeps per group (five for the first test); preview retention after plot reconnect remains undecided.

**Acceptance demonstration:** start the independent instrument server and experiment coordinator programs; author and save a plan; restart/disconnect the authoring notebook and submit the plan through a client; preflight executable policies before touching hardware; enter experiment-exclusive lockout for every registered instrument; explicitly connect the selected matching-KIND VNA under the run session, then acquire/refine/fit while the notebook may disconnect/reconnect; produce data, run report, and linked lab-timeline entry; finish and release lockout (or show a clear failure/quarantine path). A custom notebook-only policy unavailable to the fresh runner must fail preflight, not fall back to its logged source.

## Proposed implementation sequence — review between steps

1. **Driver contract and Python 3.13 baseline (first slice implemented):** a separate minimal package exists in ``; use the available Miniforge Python 3.13 and its `pip` to establish development/tests without importing V1's heavy dependencies. Port the small SCPI command/transport core and then **AgilentN5183A, YokogawaGS200, AgilentE8363C and AgilentN5230A** selectively, reviewing interfaces after the first driver. Test command generation, conversion, limits/ramps, fake VISA I/O and VNA complex-trace decoding without hardware; keep real-device smoke tests opt-in. Test Holzworth-like physical identity and import side effects with a fake, without yet porting the driver. QGL/bbndb remain optional. Existing V1 CI targets Python 3.8; inability to collect V1 tests in the inspected Python 3.13 environment due to missing dependencies is not evidence those tests fail in a supported environment.
2. **Specify the service boundary together (instrument side reviewed and prototyped):** explicitly started instrument server versus experiment coordinator, local IPC and sessions, registration and domain-wide lockout, worker/run states, notebook disconnect, and service crash/recovery. Sketch the VNA experiment/plan and policy only far enough to check that the instrument protocol supports them. Review contracts *before* building service infrastructure.
3. **Independent instrument server (laboratory slice implemented):** local Unix-socket service, explicit connection, process-backed workers, domain-wide exclusive run/live ownership, GET/SET/CALL with a session-bound instrument proxy, and bounded inline NumPy VNA traces (protocol version 4, 8 MiB total result limit). The pyqtgraph/PySide6 inventory GUI shows separate connection and ownership states and supports Connect, Disconnect, Recover, Terminate, Disconnect All, Clear Instruments and Terminate All; it now supports discovered VISA registration, but cannot use instrument measurement data/settings. The interactive headless CLI `shutdown` disconnects, clears, and exits only on success; Ctrl+C retains registrations. Forced `-c`/`--clean` discards persisted registrations and run state without hardware I/O. See [STATUS.md](STATUS.md) and the [operator guide](../src/auspex_v2/instruments/server/instrument_server.md) for details and safety limits. The explicit registry admits simulators and the ported N5183A, E8363C, N5230A and GS200 under fixed KINDs. PyVISA-py is enforced; per-instrument command/I/O timeouts are configurable and whole-command deadlines default to None. Registry status and forced termination remain available during connection, GET/SET/CALL, and disconnection waits. VNA coordinates deliberately retain V1's linear-sweep assumption; actual stimulus-vector readback is deferred. There is no automated physical-device validation, durable lab notebook, or digitizer transport.
4. **V2 data store and experiment service implemented for writer-only fixed sweeps:** version 2 self-describing `.dat` files contain value arrays and actual coordinates (shared, dependent, or ragged), names/units, and an index manifest; an optional JSON settings snapshot is separate. Old V2 version 1 and V1 data are not read. The persistent local experiment program now supervises saved-plan execution, run status, writers and reconnecting notebook/CLI clients. Incremental/adaptive acquisition and plot subscriptions remain next steps; no coordinator GUI is necessary yet.
5. **Simple process-per-filter pipeline (initial graph supervisor implemented):** the in-process reference and single-worker harness remain. `FilterServer` now supervises a single-ingress DAG of spawned passthrough/complex-average workers from a dedicated thread, with direct shared-memory edges, bounded framed-JSON notification queues, overlapping windows, bounded named results, both capacity policies, local configuration revisions, and failure/cancellation cleanup. Offline tests include a two-process VNA smoke test and independent averaging branches. The dedicated store-owner process now multiplexes required writer sinks and acknowledges completed scan publication. The runner owns explicit scan boundaries and actual sweep positions; filter groups cannot cross scans. Complete Cartesian sweeps form named dimensions; irregular paths use a point dimension; varying-length rank-one traces use offsets. The optional standalone read-only dark PySide6 graph viewer attaches locally via a private Unix socket and manually refreshes last-acknowledged configurations, schemas and topology. It is not a plot client or graph editor. The separate read-only pyqtgraph DataBrowser watches multiple OS folders for immediate V2 run children and accepts individual run folders, plots only published 1D datasets, manually refreshes all inventories with a GUI button or menu, and shows nested run/file metadata; multidimensional and ragged files are visible but not plotted. Whole-scan graph filters, TCP plot subscriptions/reconnect integrated with the eventual experiment coordinator, automatic settings/events capture, custom filter admission, multi-source inputs/joins, and full coordinator integration remain deferred.
6. **VNA demonstration:** review admitting the already ported direct-use E8363C driver to server workers, test acquisition and fit behavior, and record human-readable results and lab timeline. Review safety and instrument configuration before hardware tests.
7. **Throughput milestone:** choose a representative raw digitizer with measured sample rate, channels, chunk size, run length, and retention needs. Benchmark buffer/copy/processing budgets before proposing placement or fan-out optimization.
8. **Later:** optional QGL/qubit adapter and migration of valuable V1 filters/drivers/calibrations; CLI/GUI operational polish. No blanket conversion of V1 inheritance hierarchies or promise to run every V1 experiment unchanged.

## Open questions for interactive review

- Real drivers are now explicitly admitted for trusted lab use without making typed operation schemas, automatic physical identity checks, or safety verification prerequisites. Recovery acknowledges operator inspection and marks `DISCONNECTED`; it is not physical readback and its note is not a durable audit record.
- The first symbolic `sequence(self, seq)` compiler syntax is implemented; review feedback before integrating acquisition adapters, driver KIND matching/explicit command contracts, and filter-result operations. Keep hardware-specific operations in drivers, not inferred from their members.
- How do we identify and load custom decision functions for **the immediate run** while ensuring a fresh controller rejects an unavailable/changed function? What minimum policy provenance is useful without packaging notebook environments?
- The implemented ExperimentServer IPC acquires/releases the instrument-server run session from its supervised runner, connects only required instruments, and orphans ownership on runner/supervision loss. Both programs use explicit local Unix sockets and one active run per host; remote discovery/authentication remains out of scope.
- How does the VNA expose a single atomic `get_trace` acquisition (including its current restart/continuous-mode behavior) through the command/buffer interface? What real instrument address, safe power/IF bandwidth, and measurement S-parameter should be used for hardware testing?
- What schema/chunk limits and pipeline buffering will be needed for the eventual digitizer target? Determine these from an actual hardware workload rather than the VNA's small trace.
- What run-level plan/status/event layout and log granularity should extend the V2 `.auspex` manifest? V1 file compatibility is not required.

## VISA discovery and terminal registration (implemented)

- Current focus is usability. The user reports an attended hardware-in-the-loop test confirming the basic experiment, InstrumentServer, and filter pipeline path; this is not a model-by-model validation or evidence for adaptive fitting/throughput.
- Both launcher consoles and the standalone instrument terminal support `enumerate visa`, `identify <letter|all>`, and `register <letter> <driver name>`. Enumeration replaces a session-local candidate snapshot (`a`…`z`, `aa`…); inventory IDs remain numeric. Candidates show resource, suggested driver(s), identity/error, serial and registered status. Enumeration is not proof that an instrument exists.
- `identify all` requires y/n confirmation, skips serial and registered resources, and probes sequentially. Explicit letter identification can probe serial. Server-side temporary VISA connections send only `*IDN?`, with one-second open/I/O timeouts and guaranteed close attempts. Discovery excludes run/live ownership, and an active probe prevents new leases/registration without blocking status.
- Each driver inherits `IDN_STRING = None`; admitted real VISA drivers supply a literal, case-sensitive substring. All matching drivers are advisory; registration always requires an explicit admitted driver and prompts for an inventory name. ## Code readability and documentation convention

- **Human maintainability is a design constraint.** Code must be explainable, concise in purpose, and clear enough for an unassisted human to modify safely. Prefer explicit names, straightforward control flow, small cohesive components, and visible state transitions over clever compression or abstraction. Reasonable verbosity is welcome when it makes behavior, failure modes, or ownership easier to understand. Review new interfaces and non-obvious code paths from the perspective of someone reading them without the original author; do not trade clarity for fewer lines.
- Give **every class** a brief purpose docstring. Give **non-trivial methods** (roughly more than 10–12 lines, including test methods) a one-sentence docstring explaining their intent or contract; do not merely restate the method name. Short, self-explanatory methods do not need one. Keep these comments accurate as the code evolves.

## Agreed pipeline and ExperimentServer demonstration plan

### Pipeline construction slice (implemented)

- One shared authoring API, independent of experiments: explicit `PipelineInput` list, V1-style `(producer_port, consumer_port)` edges, nodes discovered from edges, explicit unique names. Definitions are inert, not process/queue owners. New objects live in `filters.definitions` to preserve existing executable processor imports.
- Schema inference from supplied input contracts, optional explicit input schemas, simple structural/local checks rather than exhaustive possible-data validation. Actual grids/lengths travel with windows; filters reject incompatible actual data. General multidimensional ragged arrays remain unsupported by the current runner.
- Ordinary configuration attributes, no `.value`; document that compile/manual startup takes a detached snapshot. No mutation warning on later definition edits.
- Simple filters use sink/source; multi-output filters use descriptive names only. Current definitions: Passthrough, ComplexAverage (final_average/partial_average), WriteToFile and DataBuffer. Required sinks cannot consume partial previews. Buffer access belongs to the running pipeline, not the definition.
- Plain JSON save/load for definitions and compiled snapshots. Single-ingress ManualPipeline adapter, preserving older explicit NodeSpec recipes. Exact writer dataset names support one scan per execution initially, rejecting a second scan rather than silently naming or overwriting it.
- Named multiple inputs and explicit EmptySource bindings are API-only for now. Empty means no windows, with normal scan/run lifecycle signals in the future runner; it does not mean zeros or an empty array. All declared inputs must be wired. The current runner rejects multi-input/empty recipes before allocating execution resources.

### Experiment/compiler integration (implemented offline)

- New compilation emits version-5 execution units with resolved pipeline schemas/connections; incompatible earlier versions fail immediately with guidance to recompile. Saved nested pipeline documents now reject unknown fields too. PipelineExecutor is an explicitly offline, single-pipeline harness: injected command results, virtual WAIT, real processing/storage, no leases or service supervision. Legacy ACQUIRE is no longer an instruction; multi-input/empty execution remains unsupported. The authoring API uses CALL plus explicit PUBLISH. Test coverage includes saved-plan execution in a fresh process without authoring classes.
- Named PipelineInput objects belong to their PipelineDefinition so external connections identify the whole graph. Compiler and loader validate every input binding, published output connections and schema agreement. Syntactically unused output declarations are allowed; there is no reachability analysis.
- Result selection supports strings and integer tuple/list positions; implicit unpacking/iteration of symbolic results raises guidance. PUBLISH is restricted to the main scan, including sweep hooks. The harness seals a completed scan before teardown, then waits for required processing/publication afterward. Teardown stops on error; completed data can still publish. Failed partial scans are cancelled. Successful early termination finalizes the admitted prefix, subject to required-group completion.

- Class-level `OutputConnector(dtype=..., dimensions=..., axis_units=...)` declarations. Read explicitly, then `seq.publish(self.trace, data=result[...], axes={...})`; do not infer publication from driver methods or interpret instrument-specific return objects implicitly.
- One publication is a complete acquisition window, not a scan. Several publications may share a sweep point. Submission may block for capacity but is not a processing/publication acknowledgment. The runner supplies sweep coordinates; manual callers supply theirs.
- External `exp.connect(output, pipeline_input)` or internal `setup_pipeline(self)`. Default `setup_pipeline=None` is ignored. Internal setup runs during compilation on the detached recording copy, before recording measurement hooks, using configured values and performing no instrument I/O.
- Internal and external wiring are mutually exclusive: any external connections skip/replace internal setup with an explicit warning; subsequent external connections build that external configuration. Require a pipeline, connected published outputs, and a source for every declared pipeline input (including explicit EmptySource). Checks are syntactic, not exhaustive branch-reachability analysis.
- The experiment plus attached processing definition is the execution unit. Save the detached processing configuration with the experiment plan and run data.

### First ExperimentServer demonstration (writer-only laboratory slice implemented)

- Main story: submit a saved fixed-sweep experiment using simulated or admitted matching-KIND instruments; close the notebook; reconnect and inspect completed data and execution log. One trace per point through passthrough and a required writer; no averaging required for this demonstration. Instruments remain connected after successful finalization.
- `client.submit(plan, name='my_experiment', dir='/path/to/data/', date=False)` submits to an explicitly started server and returns an accepted run handle promptly. The server allocates a unique `my_experiment_NNN.auspex` directory without overwriting; writer-defined group/dataset names live within the one run store. Name/directory are submission options, not changes to compiled measurement instructions.
- Client queries: active_run, list_runs, get_run; handles provide status, optional wait, cancel and run ID/path. Notebook disconnect does not cancel a run. One active run, no queue; a second submission is rejected as busy. No separate server-side open-but-unsubmitted experiments.
- Cancellation is a request, not an instantaneous hardware stop. Stop at interruptible boundaries, attempt teardown, retain completed published scans, discard the unfinished scan, and expose cleanup failures. Cancelling the single-scan demo midway leaves plan/log but no measurement dataset. Uncertain instrument command outcomes are not automatically retried.
- Ownership, fixed-KIND admission, store-directory handoff, cancellation and crash/restart reconciliation are implemented and simulator-tested; this is not model-specific physical-device or throughput validation.

### Reviewed resource contracts (offline building blocks implemented; service deferred)

- ExperimentServer owns `client.submit(plan, name=..., dir=..., date=False)` and a volatile catalog. Plans deliberately have no submission method; auto-cleanup is deferred. `run.release_buffers()` frees only temporary results; `run.cleanup()` removes a **terminal** run from that catalog and releases its buffers without deleting files. Auto-cleanup does this at finalization. `run.wait()` must still return durable terminal outcome via its known folder when auto-cleaned. No automatic catalog rediscovery after server restart; saved folders remain inspectable by path.
- Read-only `preflight_run()` validates supported pipeline topology, declared graph budgets and the 8 MiB inline server-buffer transport limit before folder allocation; a future service must also reserve its single-run slot and retained-buffer budget first. Operational failures after claim retain a FAILED folder. Buffers are intentional **non-persistent temporary data**, not queues that require a client consumer during a server run. In unattended execution they fail clearly at capacity, independent of graph-edge backpressure; manual pipelines retain their default consuming/blocking option. A server-wide byte limit budgets the sum of each buffer's capacity times its declared schema maximum before admission. Completed batches transfer into server-owned memory before terminal status, survive notebook disconnect, and disappear at explicit release/cleanup or server stop. `RetainedRunBuffers` currently tests in-process reservations and independent snapshots; bounded buffer IPC and auto-cleanup still need implementing; writer-only run handles now exist.
- The server claims `name_NNN.auspex` (start `000`, advance beyond the largest existing number, retry atomic collisions), initializes an empty manifest and `UNINITIALIZED` status stub, then atomically saves plan and immutable run metadata and advances to `ACCEPTED` before returning a handle. Errors after the stub leave a failed or uninitialized folder, never a reused number. Writer processes open an **explicitly preallocated** store in append mode; only they update datasets and manifest. Server owns status/events/logs separately. No writer is needed for buffer-only or startup-failed runs. `RunFolder.allocate`, explicit `existing_store=True` handoff and offline tests exercise this contract without implementing a daemon.
- Version-3 compilation has no legacy `graph` plan field or `seq.acquire` instruction. Attempting `set_graph()` or assigning `Experiment.outputs`/`graph` fails immediately rather than saving inert wiring. Previous compiled plan versions are deliberately rejected. The package reorganization retains documented old browser/fake/pipeline import paths as small module-import compatibility shims (unrelated to plan formats).

### Accepted run lifecycle policies (writer-only laboratory slice implemented)

- Public submission is `client.submit(plan, name=..., dir=..., date=False)`, not a plan method. `dir` is absolute and existing; `date=True` inserts the host-local `YYYY-MM-DD` directory. First demo is writer-only; incremental acquisition and bounded buffer transfer follow separately.
- Service status is authoritative (`ACCEPTED`, `RUNNING`, terminal); setup requires a persisted RUNNING acknowledgment. Logs are best effort and have no acknowledgments; no events file yet. Status-write failures disable new admission and prominently explain unresolved durable state and lease release. Startup never scans folders or restores catalog entries.
- Runner owns the instrument connection. Death or teardown failure closes without END_RUN, orphaning the lease. Pre-setup failures release the lease; successful teardown releases it before processing drain. Cancellation is cooperative at command boundaries and never interrupts teardown. Teardown failure takes precedence over cancellation.
- One service/runner IPC connection suffices. Control is checked before instructions and during bounded wait intervals; no watchdog, no attempt to undo in-flight commands. Filter health is checked before new measurement commands. Future buffer transfer is end-of-run, one bounded acknowledged batch at a time; partial transfer is discarded on failure, and the run fails while disk publications remain. The current inline 8 MiB array encoding is the intended first transport; mmap digitizer transport is deferred.
- Admission/startup order: validate saved unit and instrument mappings/KINDs; allocate run directory and persist accepted plan/status; acquire the instrument run lease and recheck admission; start pipeline/store owner and await readiness; connect required instruments; enter recorded setup and measurements. Already-connected instruments are reused. Never implicitly register or recover instruments.
- Failure before setup begins cleans up runtime resources without executing experiment teardown. Connections already completed remain connected and are reported. Once setup begins, attempt teardown on success, failure or cancellation, including partial setup failure.
- Teardown is the experiment's attempt to safe hardware, not proof of physical safety. Stop on its first error, prominently identify the failed instruction and skipped remaining cleanup, retain the original execution failure separately, and require explicit recovery/reconciliation. Do not retry or keep issuing hardware commands after a teardown error.
- Teardown failure means FAILED and retains the instrument-domain lockout. Instrument recovery and orphan-run reconciliation remain distinct; clearing a run lock cannot replace recovery of a quarantined instrument. Execution/processing failure with successful teardown permits normal lease release but never clears an InstrumentServer recovery requirement.
- Normal completion seals the scan, runs teardown promptly, then waits for required processing/publication. The run remains finalizing until both are resolved. Retain completed published datasets even if teardown fails; publication is not evidence of overall run success.
- Ordinary cancellation must not interrupt teardown; repeated cancellation requests do not skip cleanup. Operator termination remains a separate forceful operation. Command deadlines and explicit teardown waits still apply.
- No automatic resume or replay after server restart. Previously active runs become interrupted/outcome uncertain; retain saved plans/logs/published data and require explicit reconciliation/recovery.
- A surviving runner that detects ExperimentServer loss stops all further execution, including teardown, even if InstrumentServer is alive. Already dispatched commands may complete with uncertain outcome. Retain lockout for operator reconciliation; never automatically issue further hardware commands in this uncertain environment.
