# Auspex V2 — working plan

**Status:** collaborative design, not an implementation mandate. This document records decisions, assumptions, open questions, and the next small steps so we can resume the discussion without rediscovering them. **Do not implement the whole plan autonomously:** discuss interfaces and review each vertical slice together before proceeding.

## Goal

Evolve Auspex into a Python 3.13 general-purpose experimental-control system while retaining the V1 mental model: define an experiment as a Python class with parameters, instruments, outputs, a single-measurement kernel, sweeps, and a filter graph. Add a compilation boundary so a saved plan executes independently of changes to a Jupyter notebook. Preserve convenient direct Python access to instrument drivers. Support adaptive measurements and real CPU parallelism in the processing pipeline.

We are **not** building LabRAD, a distributed instrument service, a hermetic application packager, or arbitrary interrupted-run resumption. The initial deployment is local to one acquisition host. Qubit experiments remain a future compatibility target, not the first implementation target.

## Agreed design

### Experiment authoring and plans

- Continue to use Python experiment classes and familiar concepts such as class-level parameters, output connectors, `add_sweep(...)`, and `set_graph(...)`. V1 references: `src/auspex/experiment.py`, `src/auspex/parameter.py`, `src/auspex/stream.py`, `doc/experiments.rst`.
- `exp.compile()` freezes and validates the configured experiment into a saved, inspectable plan; `auspex.run(plan)` executes it. Editing notebook variables or the original experiment after compilation must not alter that plan. A freshly started controller must be able to **start** a supported saved plan without re-running the notebook. No requirement to resume a failed or interrupted run.
- Arbitrary imperative V1 `run()` code cannot be converted reliably into a portable command program. Explore a V1-like `sequence(builder)` method that constructs typed instructions for one measurement, while sweeps repeat it. This is a **proposed API**, not a settled syntax. The plan can encode allowed control flow and adaptive decision points, without knowing in advance which path observations will select.
- Compilation should validate command parameters, instrument capabilities, sweep/axis and filter schemas, permitted transitions, and bounds. It need not inspect arbitrary filter code or package an entire Python environment. Hardware connections occur at run time, not while declaring classes or compiling.
- A supervised experiment runner interprets the saved plan; it does not execute recorded experiment source. Plan format needs a small explicit version number and a readable `explain()` representation. Keep code/plugin compatibility checks pragmatic rather than promising perpetual portability. The notebook/CLI/GUI is only a client: disconnecting it must not stop an active run.

### Adaptivity

- A measurement and its completed processing result enter a decision point. A **pure decision function** receives the result, explicit previous policy state, and frozen configuration, and returns proposed next settings and/or sweep points, updated policy state, or stop/failure. The experiment runner validates bounds and iteration limits, records the decision and its inputs, then requests commands through its exclusive instrument-coordinator session. No instrument handles or side effects inside decision functions; randomness, if needed, is represented by explicit state/seed.
- Built-in, versioned policies support saved-plan execution immediately. Custom policies can be referenced by module/function with a code/version check. Truly reusable experiment definitions and decision functions should be committed to the Auspex repository as a **human/lab practice**, not a source-control rule enforced by `compile()`.
- Notebook-only decision functions are useful for exploration. Their source may be saved for human inspection, but a saved plan **must fail preflight** if its executable decision function is unavailable to a freshly started controller. Never execute logged source as an implicit fallback or silently substitute a changed policy.
- Do not claim that identical plans produce identical physical measurements or adaptive paths: record actual commands, observations, decisions, and sweep coordinates. Distinguish replaying recorded decisions from recomputing them if replay is added later.

### Local services, control, and instruments

- Run **two independent, persistent local programs** on the acquisition host, started explicitly rather than launched by a notebook. The **instrument coordinator** owns registered-instrument inventory, exclusive run/live sessions, worker processes, failure/recovery state, and instrument events. The **Auspex experiment coordinator** accepts saved plans, supervises experiment-runner and filter processes, owns run status/results, and records experiment events. Notebook, CLI, and future GUI clients connect to these programs; they do not own the backing processes. A notebook can disconnect and reconnect while a run continues.
- There is **one authoritative instrument coordinator per acquisition host**, not a new instrument coordinator for each experiment. Each experiment runner uses exactly one exclusive run session with it; this is the intended one-to-one *session* relationship, not process ownership. Instrument coordinator registration/leases provide the host-wide authority that prevents independently submitted runs or live clients from claiming the same domain. Initially, allow only one active run per host. Define the lifecycle and protocol boundary before implementing experiment authoring.
- Use a small local-only IPC request/reply protocol and explicit connection/version handshake; unlike V1's plot server (`utils/auspex-plot-server.py`), do not bind instrument control to all network interfaces by default. Keep bulk data off control IPC. The specific transport, authentication/access permissions, discovery, and startup ordering remain to be decided.
- Instruments registered with the instrument coordinator constitute an exclusive laboratory domain. At the start of an experiment, **lock out interactive Auspex access to all registered instruments**, not just the devices used by that experiment (analogous to remote mode). Lockout is not a command to reset or configure unused hardware. To use one independently during a run, de-register it *before* the run. Registration/de-registration and recovery are explicit, logged actions; de-registration must not bypass an active run or an unsafe/uncertain state. This protects cooperating Auspex clients, not someone connecting outside Auspex directly.
- A driver remains easy to use in a notebook or a quick Python loop while no experiment holds the domain. **Registered** instruments are accessed interactively through a client of the independent instrument coordinator (prefer a synchronous proxy over a second unmanaged connection); the same lockout rules apply. **Unregistered** instruments can still be used directly as ordinary Python drivers. Experiment orchestration must not be required for simple lab scripting.
- Default proposal: one spawned **process-backed worker per active physical instrument connection**, rather than per channel, for independent termination and native-library isolation. Each worker constructs/connects its driver inside its process and serializes its commands. Benchmark startup and IPC; thread-backed workers could be an explicit exception, but Python threads cannot be forcibly terminated safely.
- Lightweight coordinator-to-worker command language: **`GET`, `SET`, and `CALL`** with typed arguments, results, correlation IDs, timeouts, and an allowlist/capability declaration. `GET`/`SET` address declared commands or managed properties; `CALL` addresses explicitly registered handwritten methods and may return data, trigger acquisition, or both. Do not infer wire operations from return type or method name; generated Python `get_`/`set_` helpers are not extra `CALL`s. Avoid exposing arbitrary raw SCPI or arbitrary method invocation to compiled plans. Batch commands when appropriate. Bulk acquisition data does **not** travel in control messages.
- A terminated or unexpectedly dead worker enters a latched **TERMINATED** state: any in-flight command has an unknown outcome; do not silently retry, release for another run, or infer that the physical device is safe. `TERMINATED → IDLE` needs explicit operator recovery/checks, available from CLI and eventually a small GUI, and logged with operator identity. Killing a process does not switch off a source or stop a magnet: driver-specific safe shutdown and hardware interlocks remain separate concerns.
- If the **experiment coordinator or runner** dies mid-run, the instrument coordinator must not infer that the domain is free: retain the lockout and require explicit reconciliation of the orphaned/uncertain session. If the **instrument coordinator** dies, the experiment fails and hardware state is treated as uncertain. Restarting either program does not automatically resume the run. Define recovery after normal shutdown, client disconnect, and process crash separately.
- Preserve V1's declarative driver authoring (SCPI commands, generated properties and `get_`/`set_` methods, value conversion and bounds) without copying its class-name-dependent metaclass or eager import of all drivers (`src/auspex/instruments/instrument.py`, `src/auspex/instruments/__init__.py`). Keep command definitions inspectable for coordinator metadata. Explicitly implemented operations/properties must also be registerable: **SCPI descriptors are not mandatory for every instrument**. Custom acquisition drivers such as X6/Alazar currently couple reception to output connectors and will need streaming adapters; a command-only wrapper is not sufficient.
- Holzworth (`src/auspex/instruments/holzworth.py`) is the counterexample to a SCPI-only design: it has USB/DLL backends, handwritten properties, limits learned at connection, and multiple logical channels on one physical device. Resource ownership must use a physical-device identity (e.g. serial shared across channels), not assume a worker per channel. Importing a driver must not probe/reset hardware or load an unavailable backend; connect explicitly inside the worker and report failures rather than substituting a `MagicMock`. Test these constraints with a fake multichannel backend before porting Holzworth.

### Filter pipeline

- Keep V1-like output/input connectors and graph edges for authoring, but compile a dataflow DAG separate from the experiment control graph. A named, window-complete processing result bridges back to an adaptive decision; filters do not issue instrument commands.
- Prefer a **simple first implementation: one logical filter instance per process**, as in V1, with no automatic process-placement compiler or introspection of filter internals. Each graph edge gets its own bounded shared-memory channel (a ring of reusable slots). Producer writes a free slot; a small ready message carries slot ID, actual shape/length, schema and run/acquisition/window/sequence IDs; consumer releases the slot when done. Fan-out initially copies to each edge rather than introducing global reference counting. Benchmark before considering explicitly grouped filters or zero-copy fan-out.
- Define filters independently of process/queue inheritance: declared ports and schema transformation, `on_batch`, `on_window_end`, and lifecycle hooks. Retain axes, units, dtype, and unstructured/adaptive coordinates as explicit metadata. Completion of a window is an explicit ordered event, **not** a test for an empty queue.
- Bounded edge capacity provides backpressure. Required data and adaptive results must not silently drop; live preview may be explicitly best-effort. For hardware that cannot pause, provision and benchmark adequate buffers/throughput and fail clearly if capacity is exceeded. Do not interpret a small VNA demo as proof of raw-digitizer throughput.

### Data, run log, and lab notebook

- Extend V1's folder-based `.auspex` data format (`src/auspex/data_format.py`) with versioned run-level metadata: frozen plan, actual acquisition coordinates, data descriptors, decisions, status, and a detailed run log. Preserve data/metadata separation and provide a deliberate strategy for reading older V1 folders.
- Include a human-readable **run report**, linked to machine-readable events and arrays. Best-effort source provenance: save a *non-standard experiment definition* and decision-function code used by that run when available. Source is for human reference only, not authoritative, guaranteed complete, or executable; do not dump full notebook history. Make capture failures visible. Consider secrets/file permissions when saving or sharing source.
- Maintain a **host-level lab notebook**: a sparse, readable timeline combining high-level events from the experiment coordinator (runs and user comments, with links to run folders) and instrument coordinator (interactive connections, de-registration, worker failure, recovery). Define a single ordering/persistence mechanism for the combined timeline; neither program should invent the other's internal state. It is a backstop to human notes, **not a per-command trace**. Provide a separate current instrument view whose values are labeled last-commanded, last-observed, or unknown, rather than implying certainty about hardware state.
- On service restart, an interrupted run is incomplete/failed; instruments with uncertain physical state require reconciliation, not automatic resumption or automatic return to IDLE.

## First vertical slice: find a VNA resonance

Target existing `AgilentE8363C` (`src/auspex/instruments/agilent.py`), whose driver exposes `frequency_center`, `frequency_span`, `num_points`, and `get_trace()` returning frequencies and complex S-parameters. First use a simulated E8363C-like device; real instrument integration follows review of the simulation.

**Scenario:** acquire ~2000 points over ~1 GHz, find a candidate ~1 MHz-wide resonator, narrow the sweep, fit a Lorentzian, and finish with the fitted linewidth occupying roughly 50% of the final span (approximately 2 MHz for a 1 MHz linewidth). Specify whether the fit uses magnitude, power such as `|S21|²`, or a complex response, and whether it seeks a peak or dip. At 1 GHz / 1999 intervals the initial spacing is ~500 kHz: the first sweep has only ~2 samples across a 1 MHz feature. Use the coarse sweep for *candidate detection*, not a trustworthy linewidth fit; an intermediate sweep (e.g. ~20 MHz) may be required. Fit-quality checks, no-candidate behavior, edge-of-span behavior, frequency bounds, and a maximum number of refinements must be explicit.

**Acceptance demonstration:** start the independent instrument and experiment coordinator programs; author and save a plan; restart/disconnect the authoring notebook and submit the plan through a client; preflight executable policies before touching hardware; enter experiment-exclusive lockout for every registered instrument; acquire/refine/fit with the simulated VNA while the notebook may disconnect/reconnect; produce data, run report, and linked lab-timeline entry; finish and release lockout (or show a clear failure/quarantine path). A custom notebook-only policy unavailable to the fresh runner must fail preflight, not fall back to its logged source.

## Proposed implementation sequence — review between steps

1. **Review the driver contract, then establish the Python 3.13 driver baseline:** a separate minimal package exists in `v2/`; use the available Miniforge Python 3.13 and its `pip` to establish development/tests without importing V1's heavy dependencies. Port the small SCPI command/transport core and then **AgilentN5183A, YokogawaGS200, AgilentE8363C and AgilentN5230A** selectively, reviewing interfaces after the first driver. Test command generation, conversion, limits/ramps, fake VISA I/O and VNA complex-trace decoding without hardware; keep real-device smoke tests opt-in. Test Holzworth-like physical identity and import side effects with a fake, without yet porting the driver. QGL/bbndb remain optional. Existing V1 CI targets Python 3.8; inability to collect V1 tests in the inspected Python 3.13 environment due to missing dependencies is not evidence those tests fail in a supported environment.
2. **Specify the service boundary together:** explicitly started instrument coordinator versus experiment coordinator, local IPC and sessions, registration and domain-wide lockout, worker/run states, notebook disconnect, and service crash/recovery. Sketch the VNA experiment/plan and policy only far enough to check that the instrument protocol supports them. Review contracts *before* building service infrastructure.
3. **Independent simulated instrument coordinator (first prototype implemented):** explicitly started local program with registration, synchronous live client, all-registered-instrument run lockout (atomic rejection if any live sessions are open), process-backed simulated workers, GET/SET/CALL, orphaned run lockout and explicit termination/recovery. Versioned IPC supports by-value framed numeric NumPy arrays for simulated VNA traces (8 MiB aggregate result limit), alongside JSON control. Offline integration tests cover these paths. The allowlist remains simulated-only (`simulated_source`, `simulated_vna`); real-device readiness, recovery checks, lab notebook, shared-memory buffers and experiment supervision remain future work.
4. **Experiment coordinator and plans:** persistent local experiment program with supervised runner, saved plan compilation/loading, simulated VNA decision barriers, run status, and notebook/CLI clients that can disconnect/reconnect. No GUI necessary yet.
5. **Simple process-per-filter pipeline:** validated graph, bounded per-edge channels, explicit window completion, required result delivery, cancellation/error tests, and basic run-folder logging.
6. **VNA demonstration:** adapt the real E8363C driver, test acquisition and fit behavior, record human-readable results and lab timeline. Review safety and instrument configuration before hardware tests.
7. **Throughput milestone:** choose a representative raw digitizer with measured sample rate, channels, chunk size, run length, and retention needs. Benchmark buffer/copy/processing budgets before proposing placement or fan-out optimization.
8. **Later:** optional QGL/qubit adapter and migration of valuable V1 filters/drivers/calibrations; CLI/GUI operational polish. No blanket conversion of V1 inheritance hierarchies or promise to run every V1 experiment unchanged.

## Open questions for interactive review

- What V1-style command declaration and explicit handwritten-command metadata API preserves direct driver ergonomics while supporting the coordinator, including extra-argument commands and device-specific physical ownership? Review this with the first N5183A port and a fake Holzworth-like two-channel device.
- What is the smallest comfortable V1-like `sequence(builder)` syntax? Which experiment-level operations are essential beyond instrument GET/SET/CALL (e.g. acquire/emit and bounded branches)? Which hardware-specific operations belong in driver capabilities instead of the general command language?
- How do we identify and load custom decision functions for **the immediate run** while ensuring a fresh controller rejects an unavailable/changed function? What minimum policy provenance is useful without packaging notebook environments?
- Specify the two local programs' IPC and ownership: how does an experiment runner obtain/release an exclusive session from the instrument coordinator? How do notebook clients discover and authenticate to each? How are orphaned sessions reconciled after a coordinator/runner crash? Initial policy is one exclusive run per host.
- How does the VNA expose a single atomic `get_trace` acquisition (including its current restart/continuous-mode behavior) through the command/buffer interface? What real instrument address, safe power/IF bandwidth, and measurement S-parameter should be used for hardware testing?
- What schema/chunk limits and pipeline buffering will be needed for the eventual digitizer target? Determine these from an actual hardware workload rather than the VNA's small trace.
- What is the minimal V2 folder layout and event/run-log granularity, while retaining a readable path for V1 `.auspex` data?

## Code documentation convention

- Give **every class** a brief purpose docstring. Give **non-trivial methods** (roughly more than 10–12 lines, including test methods) a one-sentence docstring explaining their intent or contract; do not merely restate the method name. Short, self-explanatory methods do not need one. Keep these comments accurate as the code evolves.
